# Data Contract

## Scope

The integrated dataset supports demand forecasting, client intelligence, inventory decisions, and clienteling recommendations for a fictional luxury retailer named Couture Atelier.

## Provenance classes

| Class | Meaning |
|---|---|
| `observed_public` | Directly loaded from a public source |
| `derived` | Deterministically calculated from observed data |
| `synthetic` | Generated by project rules |
| `scenario` | User-controlled simulation input |

Every integrated table must include `data_provenance` when fields combine multiple classes.

The observed UCI source first produces source-specific analytical marts. These are not yet the final luxury contract tables: `customer_360`, `product_catalog`, `daily_sales`, and `demand_panel` are explicitly labeled intermediate marts. The final `customers`, `products`, `transactions`, `stores`, `inventory_daily`, and `clienteling_actions` tables will be created when the synthetic Couture Atelier layer is introduced.

## Core tables

### `customers`

Required fields: `customer_id`, `home_region`, `signup_date`, `acquisition_channel`, `consent_status`, `data_provenance`.

Rules: identifiers are anonymous; names, emails, addresses, ethnicity, and inferred wealth are excluded; consent is required before clienteling recommendations.

### `products`

Required fields: `product_id`, `category`, `subcategory`, `material`, `color_family`, `collection`, `price_tier`, `launch_date`, `data_provenance`.

Rules: product IDs are unique; prices are positive when present; simulated attributes are labeled.

### `transactions`

Required fields: `transaction_id`, `customer_id`, `product_id`, `transaction_date`, `channel`, `region`, `quantity`, `unit_price`, `return_flag`, `data_provenance`.

Rules: returns are represented explicitly; future information cannot enter historical features.

### `stores`

Required fields: `store_id`, `city`, `region`, `store_type`, `data_provenance`.

Store types are `flagship`, `boutique`, `airport`, or `online`. Locations are fictional or generalized.

### `inventory_daily`

Required fields: `date`, `store_id`, `product_id`, `opening_stock`, `units_received`, `units_sold`, `transfer_in`, `transfer_out`, `closing_stock`, `data_provenance`.

```text
closing_stock = opening_stock + units_received + transfer_in
                - units_sold - transfer_out
```

Stock quantities cannot be negative, and every row must reconcile.

### `clienteling_actions`

Required fields: `action_id`, `customer_id`, `action_date`, `action_type`, `recommended_product_id`, `customer_response`, `purchase_within_30d`, `consent_status`, `data_provenance`.

Rules: recommendations are ineligible without consent; `no_action` is valid; simulated responses cannot be reported as observed conversion.

## Time and leakage rules

- Train, validation, and test periods are chronological.
- Features use only information available at prediction time.
- Product launch dates cannot be backfilled into earlier periods.
- Post-cutoff transactions cannot affect historical features.
- Customer CLV and segmentation functions require an explicit `as_of_date`; end-of-period reports must state that date.

## Observed-source cleaning rules

- Exact duplicate source rows are removed before staging and counted in the quality summary.
- Cancellation invoices are retained as return events, not treated as purchases.
- Non-cancellation negative quantities, negative prices, missing required keys, and invalid dates fail staging validation.
- Missing customer IDs remain available for product and demand analysis but are excluded from customer-level features.

## Reporting rules

Every result must be labeled as observed, derived, forecasted, simulated, or scenario-based. Business impact is not described as causal without an appropriate experiment or quasi-experimental design.
